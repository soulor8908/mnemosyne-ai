# Mnemosyne · 向量数据库选型对比

> 工程视角下的向量检索后端选型，用于支撑 local-first 云笔记的语义检索能力。
>
> 评价立场：卡帕西视角（local-first、最小依赖、软件 2.0、可迁移性优先）。
>
> 配套文档：[产品设计](./PRODUCT_DESIGN.md) · [技术设计](./TECHNICAL_DESIGN.md) · [自托管方案](../docker/README.md)

---

## 1. 选型背景

Mnemosyne 是一款 **local-first 的 AI 云笔记**：

- 笔记的明文真理之源在浏览器（IndexedDB / Dexie），云端只见端到端加密密文。
- 单用户规模 < **1 万条**笔记，平均每条 200–800 字，分块后约 2–5 个 chunk。
- 语义检索在**客户端**进行：用户输入 query → 浏览器内生成 query 向量 → 在本地向量集合中检索 → 与关键词检索 RRF 融合 → 取 top-k 喂给 LLM 做引用溯源问答。
- **离线优先**：断网时检索必须可用。
- **隐私敏感**：用户笔记明文不能离开浏览器（除非用户主动 BYOK 调用外部 LLM）。
- 当前实现：`src/lib/db/embeddings.ts` 用 `idb-keyval` 存全量向量，检索时全量余弦遍历（O(N)）。

这些约束决定了"向量数据库"在 Mnemosyne 里不是常规的"服务端向量库"问题，而是"**浏览器内的隐私向量检索**"问题——只在规模超出单机能力后才考虑外迁。

### 1.1 评估目标

回答两个问题：

1. **当前阶段（< 1 万条）**：要不要换掉全量余弦？换什么？
2. **未来阶段（多用户 SaaS / 大规模笔记）**：什么时候迁、迁到哪？

## 4. 各方案详细分析

### 4.1 idb-keyval 全量余弦（当前方案）

**实现位置**：`src/lib/db/embeddings.ts`、`src/lib/ai/search.ts`

**机制**：所有 chunk 向量以 `idb-keyval` 平铺存入 IndexedDB；检索时一次性 `get` 全部向量到内存，做暴力余弦相似度计算，按相似度排序取 top-k。

**优点**

- **零依赖、零运维**：不引入任何额外库或服务。
- **召回率 100%**：暴力搜索是 ground truth。
- **完美匹配 local-first / 离线**：所有计算在浏览器，数据永不离开设备。
- **实现极简**：~50 行代码，无索引构建 / 增删同步成本。

**缺点**

- **O(N) 复杂度**：1 万条时单次检索 30–80ms（取决于设备），可感知。
- **全量加载到内存**：1 万条 × 384 维 × Float32 ≈ 15 MB，移动端有压力。
- **无法横向扩展**：超出 1 万条后体验断崖。

**适用场景**：单用户、笔记数 < 1 万、设备性能良好。这正是 Mnemosyne 当前阶段的目标用户画像。

**迁移成本**：0。已在生产。

---

### 4.2 HNSW 本地索引（项目即将实现）

**机制**：在浏览器内构建 HNSW（Hierarchical Navigable Small World）图索引。可选实现：

- `hnswlib-wasm`（C++ 编译 WASM，性能最好）
- `voy`（纯 Rust → WASM，体积小）
- 自实现 TS 版（学习成本最低，性能略差）

**优点**

- **查询复杂度 O(log N)**：1 万条查询 < 2ms，比全量余弦快 25–50×。
- **仍保持 local-first**：索引在浏览器内，数据不出设备。
- **离线可用**：与当前方案一致。
- **增量更新友好**：HNSW 支持单条 insert，不需要全量重建。
- **内存占用可控**：图结构额外开销约 1.5–2× 向量本身。

**缺点**

- **召回率 < 100%**：典型 95–98%（efSearch 调高可逼近 100%，但延迟上升）。
- **索引需要持久化**：HNSW 图结构要随笔记增删同步落 IndexedDB，首次加载需反序列化（1 万条约 100–200ms）。
- **WASM 包体积**：`hnswlib-wasm` 约 100 KB gzip，可接受。
- **调试复杂度上升**：图索引 bug 比数组遍历难定位。

**适用场景**：单用户、笔记数 1 千 – 10 万、追求浏览器内极致体验。**这是 Mnemosyne 下一阶段的路线**。

**与本项目集成难度**：低。只需替换 `embeddings.ts` 的存储与查询层，对外接口（`search(queryVec, topK)`）保持不变。预计 2–3 天工作量。

**迁移触发条件**：笔记数 > 1000 且用户反馈检索慢；或移动端内存告警。

---

### 4.3 Milvus

**机制**：独立分布式向量数据库，支持 IVF / HNSW / DiskANN 等多种索引，独立服务部署。

**优点**

- **专业向量库**：索引算法最全，性能调优空间大。
- **横向扩展**：支持分布式集群，可承载亿级向量。
- **生态成熟**：Cloud / Kubernetes Operator 完备。

**缺点**

- **部署重**：至少 etcd + MinIO + Milvus 三个组件，资源占用高（> 2GB 内存起步）。
- **运维复杂**：组件多、版本升级链路长，不适合个人 / 小团队。
- **与 local-first 哲学冲突**：本质是服务端集中式向量库。
- **隐私边界**：服务端只见密文向量，但用户需自行运维 TLS / 访问控制。
- **过度工程**：单用户 < 1 万条规模下，Milvus 的能力用不到 1%。

**适用场景**：多租户 SaaS、亿级向量、有专职运维团队。**不适合 Mnemosyne 当前阶段**。

**与本项目集成难度**：高。需要新增服务端检索 API、密文向量同步链路、鉴权与多用户隔离，且破坏"检索在客户端"的现有架构。

---

### 4.4 Qdrant

**机制**：Rust 实现的向量数据库，单二进制部署，支持 HNSW + 量化（Scalar / Product Quantization）。

**优点**

- **轻量**：单二进制，无外部依赖，镜像约 50 MB。
- **Rust 性能**：单机 10 万 – 百万级向量查询稳定 < 5ms。
- **部署简单**：`docker run qdrant/qdrant` 即可，适合自托管。
- **过滤能力强**：支持 payload 过滤 + 向量检索组合，对笔记元数据过滤友好。
- **资源占用合理**：10 万向量约 200–400 MB 内存。

**缺点**

- **仍是服务端方案**：与 local-first 冲突，浏览器离线时不可用。
- **密文向量检索**：服务端拿不到明文，只能做密文向量近邻，体验有限。
- **多了一跳网络**：浏览器 → Qdrant 服务，增加 5–20ms 延迟。
- **运维仍需成本**：备份、监控、升级。

**适用场景**：1 万 – 10 万条规模的自托管单用户 / 小团队，且愿意接受"检索走服务端"的架构变更。是 Mnemosyne **若要做多用户 SaaS 版**时的首选过渡方案。

**与本项目集成难度**：中。需要服务端新增 Qdrant 客户端、密文向量同步、检索 API；客户端改为"发 query 向量到服务端拿 top-k"。约 1 周工作量。

---

### 4.5 pgvector

**机制**：PostgreSQL 扩展，新增 `vector` 类型与索引（IVFFlat / HNSW）。

**优点**

- **复用现有 PG**：如果业务本来就有 Postgres（用户系统、计费、审计），零新增组件。
- **事务一致性强**：向量与元数据在同一事务里，ACID 保证。
- **SQL 生态**：可结合 `WHERE` 过滤、JOIN 笔记元数据，灵活。
- **托管 PG 服务多**：RDS / Supabase / Neon 都内置 pgvector。

**缺点**

- **性能不如专业向量库**：IVFFlat 召回波动大，HNSW 索引在 PG 里构建慢（10 万条建索引 30s+）。
- **规模上限低**：百万级以上明显力不从心。
- **仍是服务端方案**：与 local-first 冲突。
- **依赖 PG 运维**：备份、VACUUM、连接池等 DBA 工作。

**适用场景**：**多用户 SaaS** 且已有 Postgres 基础设施，向量规模 < 100 万。复用 PG 比"为向量再起一个 Qdrant"省运维。

**与本项目集成难度**：中。与 Qdrant 类似，但能复用现有 PG 连接池与 ORM，集成代码量略少。

>
> 测试假设：384 维 Float32 向量，cosine 相似度，top-10，单线程查询，浏览器端为主力设备（M1 MacBook / 中端 Android）。

## 6. 选型结论

按规模分层选型：

| 规模 | 推荐方案 | 理由 |
|---|---|---|
| **< 1 万条** | 本地 idb-keyval + HNSW（本项目当前路线） | local-first + 离线优先 + 单用户规模，HNSW 把延迟压到 < 2ms，无需任何服务端依赖 |
| **1 万 – 10 万条** | Qdrant 自托管 | Rust 单二进制轻量、性能稳定、过滤能力强；适合从"浏览器内"过渡到"自托管服务端"的场景 |
| **> 10 万条** | Milvus | 分布式能力、多索引算法、水平扩展，撑得起亿级向量 |
| **多用户 SaaS** | pgvector | 复用现有 PG 用户 / 计费 / 审计基础设施，向量与元数据同事务，运维成本最低 |

### 6.1 服务端方案为何不解决"明文检索体验"问题

Mnemosyne 的 E2E 加密链路决定了服务端只能存密文向量。即便上 Qdrant / Milvus，服务端做的也只是"密文向量近邻"——明文笔记仍在浏览器。所以服务端向量库解决的是"**规模与多用户**"问题，不解决"明文检索体验"问题。这也是为什么本项目坚持把向量检索留在浏览器内。

## 7. 本项目决策

### 7.1 当前阶段决策

**选择本地 HNSW 索引**，替换 `idb-keyval` 全量余弦。

### 7.2 理由

1. **local-first 不可妥协**：用户笔记明文不能离开浏览器。任何服务端方案都会破坏这一前提或只能做密文检索，体验打折。
2. **离线优先**：HNSW 索引在浏览器内，断网可用；服务端方案做不到。
3. **单用户规模匹配**：< 1 万条笔记，HNSW 延迟 < 2ms、内存 < 30 MB，远低于移动端承受阈值。
4. **集成成本低**：只替换 `src/lib/db/embeddings.ts` 的存储与查询层，对外接口不变。
5. **性能收益显著**：1 万条时从 30–80ms 降到 1–2ms，移动端可感知。
6. **保留迁移可能性**：HNSW 是 ANN 主流算法，未来若迁移到 Qdrant / Milvus，索引逻辑可平移，业务层无感。

### 7.3 何时迁移

满足以下任一条件时，重新评估是否迁移到 Qdrant：

- 单用户笔记 chunk 数 **稳定超过 10 万**（约 2–5 万条笔记），HNSW 浏览器内查询 p99 > 20ms 或内存 > 300 MB。
- 产品形态从"单用户 local-first"转向"**多用户 SaaS**"，需要服务端统一检索入口与多租户隔离。
- 出现"跨用户协同检索"需求（如团队共享笔记库），浏览器内方案无法满足。

迁移路径预计：

1. 服务端新增 Qdrant 客户端与密文向量同步链路。
2. 客户端检索改为"发 query 向量到 `/api/search`，服务端在 Qdrant 检索后返回 top-k chunk id"。
3. 明文笔记仍在客户端，top-k chunk 明文由客户端从本地 Dexie 取出再喂 LLM。
4. 保留本地 HNSW 作为离线 fallback，断网时降级到浏览器内检索。

### 7.4 实施建议

- **优先 `voy`（Rust → WASM）**：体积小、无需 C++ 编译链、API 友好；若性能不达标再换 `hnswlib-wasm`。
- **索引持久化**：HNSW 图结构序列化后存 IndexedDB（与 `idb-keyval` 的向量平级），首次加载反序列化。
- **增量更新**：笔记增删时单条 insert / mark delete，避免全量重建。
- **参数调优**：`M=16, efConstruction=200, efSearch=64` 起步，按召回率与延迟 trade-off 调整。
- **保留暴力搜索作为 fallback**：HNSW 索引未就绪时降级到全量余弦，保证可用性。
- **benchmark 落地**：在 `tests/` 下补一组真实笔记数据的 benchmark，避免凭公开数据决策。
